# 技术栈选型

## 选型清单

| 层级   | 选择                | 理由                       | 备选与放弃理由           |
| ------ | ------------------- | -------------------------- | ------------------------ |
| 前端   | React + TypeScript  | 团队熟悉、生态丰富         | Vue：团队不熟            |
| 状态   | Zustand             | 轻量、心智负担小           | Redux：样板代码多        |
| 样式   | TailwindCSS         | 开发快、风格一致           | CSS-in-JS：运行时开销    |
| 后端   | Node.js + Hono      | 单语言全栈、冷启动快       | Go：团队不熟             |
| ORM    | Prisma              | 类型安全、迁移工具完善     | TypeORM：类型不够好      |
| 数据库 | PostgreSQL          | 通用、JSON 字段够用        | MongoDB：事务弱          |
| 缓存   | Redis               | 标配                       | —                        |
| 消息   | （需要再选）        |                            |                          |
| 部署   | Docker + Kubernetes / Vercel / Railway | 视规模而定 |                          |
| 监控   | Sentry + Prometheus | 错误追踪 + 指标双轨        |                          |

## 决策原则

- **优先无聊技术**：除非有明确收益，否则用最主流方案
- **拒绝双数据库 / 双语言**：早期单栈，规模上来再拆
- **可逃逸**：任何选型都要有「替换成本评估」

## 不选什么及原因

- 不上 Microservices：MVP 阶段单体足够
- 不上 SSR（除非 SEO 强需求）：增加复杂度
